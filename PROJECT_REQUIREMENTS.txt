DALIMGARI VILLAGE WEBSITE - PROJECT REQUIREMENTS

PRIMARY TOP-LEVEL RULE

Before deciding or performing any project work, always read and follow this PROJECT_REQUIREMENTS.txt file. If the project owner adds a new permanent requirement, it must be added to this file. If an existing requirement is changed, this file must be updated. This file is the primary and authoritative reference for project decisions and development.

CORE REQUIREMENTS

1. The project owner has no coding knowledge.
2. The complete project must be manageable using only an Android phone.
3. The complete project must be built and completed for free.
4. No website/content information will be hardcoded inside the source code.
5. Source code will contain only structure, design, logic, and functions.
6. All website information/data will be stored in the database.
7. The database architecture must be reusable by future applications. The database must be designed as a shared, application-independent data layer so other apps can use the same database in the future.
8. Database keys and field names must be meaningful, understandable, and reusable across this website and future software/apps that use the same database. Naming must describe the data itself rather than being tied only to a specific interface.
9. Elements, components, functions, logic units, controllers, modules, layouts, files, and folders must have clear names related to their actual purpose and responsibility. Example naming concepts include controller/admin, layout/admindashboard, and module/websiteinformation. These examples are illustrative; names must accurately match their responsibility.
10. All code, file names, and folder names must use lowercase letters only.
11. Every file must be organized inside an appropriate, responsibility-based folder. Avoid unnecessary files at the project root.
12. The project must have an Admin Account System.
13. Admin Login must open the Admin Dashboard.
14. All website information must be entered and managed from the Admin Dashboard.
15. Data entered through the Admin Dashboard must be saved to the appropriate database fields.
16. Bengali will be the website's main/default language.
17. The website must be switchable to English through translation.
18. Do not use separate language fields such as Title.bn and Title.eng.
19. The website must automatically select Day/Night mode and also allow manual mode changes.
20. The homepage must have four main sections:
   1. Header
   2. Banner
   3. Body
   4. Footer
21. The homepage must have a left sidebar. The sidebar must be hidden by default and must open when the sidebar button is pressed.
22. The complete website theme, fonts, and colors must be dynamic and configurable rather than hardcoded as fixed website content.
23. The website must be responsive and designed for both mobile and web-view/desktop formats. The interface must adapt appropriately according to the device or viewport.
24. At the top of the sidebar, show the admin's round profile image, name, email, and other links.
25. Admin information must be managed through Admin Dashboard modules. Initially, the Admin Dashboard will contain two modules:
   1. websiteinformation - fields for entering and managing all website information.
   2. admininfo - fields for entering and managing the admin's information, social media profiles, and other links.
26. Additional Admin Dashboard modules will be added incrementally in the future.
27. The Admin Dashboard must also have a pagemanagement module for creating, editing, deleting, and controlling visibility of standalone pages.
28. Page Management pages must be presented as tabs or buttons arranged from the top-left of the body. Each page must have a visibility control so it can be enabled or disabled for display in the body.
29. When creating a page, the Admin Dashboard must provide a page title field and an HTML code field. The supplied HTML code must be saved in the database and the page must render according to the stored HTML code.
30. A Global Unique Field / ID System must be used throughout the entire website. Every field/data entity must have a clear, understandable, unique identifier. Internal identifiers do not need to be exposed to the project owner in the user interface.
31. The Global Unique Field / ID System must support dynamic collections of multiple records. Do not design repeated records using one generic value assignment such as page = 'a', page = 'b', page = 'c'. Each record must have its own unique identity, such as page1, page2, page3 conceptually, while the actual implementation should use a scalable unique identifier system.
32. The Admin Dashboard must also have an analysisinfo module for analytics-related functionality.
33. The analysisinfo module must show website visitor analytics and all types of visitor information that the system can legitimately and technically collect. Visitor analytics must be stored and structured so the information can be analyzed and displayed through the Admin Dashboard. Visitor information must be retained for 30 days.
34. A Global Media Upload System must be used throughout the entire website. All media fields should use the same media management architecture unless a specific location explicitly requires a separate method.
35. The Global Media Upload System must provide exactly three selectable methods:
   1. upload - upload media directly to the project's storage system and automatically obtain its URL/reference.
   2. select file - select a previously uploaded file and use only its existing link/reference.
   3. url - provide an external media URL hosted on another server/service, such as YouTube.
36. A single media field must use only one media method at a time. Upload, select file, and URL methods must not be active simultaneously for the same media field.
37. The project must recognize exactly three account/user types:
   1. admin
   2. user
   3. visitor
38. Admin accounts must be managed through Supabase. The public website must not provide a way to create an Admin account. Any account created through the website registration system must always be a User account.
39. The Admin Dashboard must have a postmanagement module for creating, editing, and deleting posts. Post creation must include:
   1. caption
   2. global media upload method
   3. album (optional)
   Posts must be displayed as database/table records below the management interface.
40. The Admin Dashboard must have a usermanagement module for viewing information about users who created accounts. Admins must be able to reset a user's password and grant special permissions.
41. A Global Permission System must be used throughout the entire website. Permissions must control who can view or change data and functions according to the assigned permission.
42. Media selected for an album must be groupable and displayable by album. Media must also be capable of being displayed as individual items or kept undisplayed, according to the stored configuration.
43. User authentication must support Google and Email/Phone with password.
44. The Admin Dashboard must have a customization module for managing website theme, fonts, colors, and related visual settings.
45. Database security must use Row Level Security (RLS) and appropriate access policies. Who can view or change data must be controlled by the permission and security architecture.
46. The Admin Dashboard must have a system module responsible for system-level functions.
47. The system module must maintain the latest 3 database backups and provide an easy mechanism to reset/restore the database from any one of those backups.
48. The system module must allow the Admin to configure what the website displays for database loading, error, and empty-data states.
49. SEO information such as page title, description, URL/slug, and related metadata must be generated/handled automatically where appropriate and must also be visible/manageable through the relevant Admin Dashboard interface.
50. The development workflow is: project owner -> ChatGPT -> GitHub and Supabase. The project must be designed so the owner can operate the development workflow from an Android phone without coding knowledge.
51. Database schema and security architecture must be designed according to these requirements and explained in simple terms when necessary. Page HTML stored in the database must be rendered through a security-conscious architecture with appropriate sanitization and protection against unsafe content.

These requirements are the core constraints for the project and must be followed during development.
